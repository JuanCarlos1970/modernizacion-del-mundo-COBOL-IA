# Casos de prueba — Gestión de Cuentas Bancarias

Matriz de casos de prueba (QA) para `gestion-bancaria.cbl` (programa interactivo) y `BATCH-CIERRE.cbl` (proceso batch de cierre). Complementa a `README.md`; no repite ahí la documentación técnica, solo la referencia cuando hace falta.

## Alcance

Cubre las operaciones principales del menú (alta, depósito, extracción, consulta, modificación, baja, reactivación) y el proceso batch de cierre. No es un reemplazo de una suite de pruebas automatizada completa: los casos lineales más simples están automatizados (ver [Testing](README.md#testing) en el README); el resto son casos manuales, pensados para ejecutarse a mano siguiendo los pasos indicados.

## Requisitos previos

- `gestion-bancaria.exe` compilado **en `bin\`** (ver README.md, sección "Dónde vive `clientes_v3.dat`"; usar `cobc -x -Wall -o bin\gestion-bancaria.exe gestion-bancaria.cbl`, con `CLIENTE.cpy` en la misma carpeta que `gestion-bancaria.cbl`). Todos los casos de esta matriz, automatizados o manuales, se corren contra **`bin\clientes_v3.dat`** — el mismo archivo que se usa siempre, no uno aparte.
- Para el caso de batch (CP-12), además `BATCH-CIERRE.exe` compilado en `bin\`, o usar `correr_batch_cierre.bat`.
- Los pasos manuales (todos salvo CP-01 a CP-04 y CP-06) se ejecutan corriendo `gestion-bancaria.exe` **desde `bin\`** (por ejemplo, `cd bin` y después `gestion-bancaria.exe`, o abriendo el proyecto en OpenCobolIDE, que ya usa `bin\` como carpeta de trabajo).
- Para los 5 casos automatizados (CP-01, CP-02, CP-03, CP-04, CP-06): la terminal donde se corre `gestion-bancaria.exe < entrada.txt > salida.txt` tiene que tener el runtime de GnuCOBOL en el `PATH`; si no, el programa falla al arrancar sin mostrar ningún error y la salida queda en 0 bytes (ver README.md, sección "Solución de problemas"). Para evitar ese problema, usar **`correr_pruebas_automatizadas.bat`**, que ya compila y corre en `bin\` con el `PATH` resuelto, y además compara automáticamente cada `salida_*.txt` contra su `esperado_*.txt` (con `fc`), mostrando un resumen OK/FALLO al final en vez de dejar la comparación para hacer a mano.

## Cómo usar esta matriz

- **Pasos a seguir** da los datos exactos (DNI, montos, opciones de menú) para que el caso sea reproducible tal cual.
- **Resultado esperado** es lo que definimos que el programa *debe* hacer, verificado contra el comportamiento real del programa al momento de escribir este documento.
- **Resultado obtenido** queda vacío a propósito: se completa a mano en cada corrida (OK / Falló + qué pasó).
- **Observaciones** indica si el caso está automatizado (y con qué archivo) o es manual, más cualquier aclaración.

## Casos de la Evolución 1 / Etapa 1: menú nuevo e INTERESES

Estos casos cubren las opciones nuevas del menú principal (6 a 10) y el submenú **8 - Intereses** (alta, modificación y baja de tasas en `intereses.dat`). **Todos están automatizados** y se corren con:

- Windows: `correr_pruebas_automatizadas.bat` (segunda parte, con su propio resumen `Resumen intereses: N OK / N FALLO`).
- Docker / CI: `bash correr_pruebas_intereses.sh` (en Docker: `docker run --rm gestion-bancaria bash correr_pruebas_intereses.sh`).

Cómo funcionan (por qué no usan DNIs ni `bin\clientes_v3.dat`):

- **Archivo vacío:** cada caso corre en una carpeta descartable, `bin\prueba_int\`, que se borra y se vuelve a crear antes del caso. Así arranca con un `intereses.dat` vacío **sin tocar nunca** el `bin\intereses.dat` (ni el `bin\clientes_v3.dat`) de verdad.
- **Fecha fija:** la fecha de proceso se fija con la variable de entorno `FECHA_PROCESO=AAAAMMDD`. Sin ella el programa usaría la fecha del día y el resultado cambiaría según cuándo se corra la prueba.
- **Pasos:** un caso puede tener varios pasos (`entrada_int04_1.txt`, `entrada_int04_2.txt`, ...). Cada paso es una ejecución del programa con su propia fecha, sobre el mismo `intereses.dat`. Hace falta, por ejemplo, para que una tasa dada de alta un día ya esté vigente al modificarla otro día. Las salidas de todos los pasos se juntan en `salida_<caso>.txt` y se comparan contra `esperado_<caso>.txt`.

Fechas usadas (octubre de 2026): 14 = miércoles, 15 = jueves, 16 = viernes, 17 = sábado, 18 = domingo, 19 = lunes, 20 = martes.

Para correr uno de estos casos a mano (Windows, desde `bin\`): `set FECHA_PROCESO=20261014`, después `gestion-bancaria.exe`, y al terminar `set FECHA_PROCESO=` para volver a la fecha del sistema. Ojo: a mano se usa el `bin\intereses.dat` real.

## Casos de la Evolución 1 / Etapa 2: PLAZO FIJO

Estos casos cubren el submenú **7 - Plazo fijo** (alta con confirmación, cancelación anticipada y consulta sobre `plazofijo.dat`). **Todos están automatizados** y se corren con:

- Windows: `correr_pruebas_automatizadas.bat` (tercera parte, con su propio resumen `Resumen plazo fijo: N OK / N FALLO`).
- Docker / CI: `bash correr_pruebas_plazofijo.sh` (en Docker: `docker run --rm gestion-bancaria bash correr_pruebas_plazofijo.sh`).

Funcionan igual que los de INTERESES, pero en la carpeta descartable `bin\prueba_pf\`: cada caso arranca con `clientes_v3.dat`, `intereses.dat` y `plazofijo.dat` vacíos, sin tocar los de `bin\`. Por eso los DNIs (`800001XX`) no chocan con ningún otro caso.

Preparación común (paso 1, miércoles 14/10/2026), salvo que se indique otra cosa: alta del cliente `800001NN` (opción `1`) y alta de la tasa `P` / `30` / `40` (opción `8`, `1`), que rige desde el jueves 15/10/2026. Las operaciones de plazo fijo se hacen en el paso 2 (jueves 15/10/2026), cuando la tasa ya está vigente.

## Notas

- Los siete casos "manuales" (CP-05, CP-07 a CP-12) tienen ramificaciones (confirmaciones S/N, submenús, estados previos que hay que preparar) que no se prestan a un script de una sola pasada; se dejaron fuera de la automatización a propósito, como se acordó.
- Si un caso falla, además de completar "Resultado obtenido", conviene anotar el `FILE STATUS` o el mensaje exacto que mostró el programa (ver README.md, sección "Solución de problemas", para los códigos de error de archivo).
- Antes de reportar un caso como fallido por "el programa no responde", revisar primero la nota del README sobre `WITH NO ADVANCING` y prompts sin salto de línea: en algunas consolas el prompt puede no verse aunque el programa esté esperando la entrada correctamente.
